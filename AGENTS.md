# ZhiFlow

A third-party Zhihu (知乎) client for Android, built with Kotlin, Jetpack Compose, and OkHttp. Under active development.

## Build System

- **Gradle wrapper**: `./gradlew`
- **Version catalog**: `gradle/libs.versions.toml` — all dependency versions live here; use `libs.xxx.yyy` accessors
- **Root `build.gradle.kts`**: only declares plugins with `apply false`
- **App `build.gradle.kts`**: applies plugins, configures SDK versions, NDK ABI filter (`arm64-v8a`), release R8+shrink, Compose build feature, source sets
- **`gradle.properties`**: `useAndroidX=true`, `nonTransitiveRClass=true`, `R8.fullMode=true`, `kotlin.code.style=official`
- **Release**: R8 minification + resource shrink + multiDex; strips `kotlin.jvm.internal.Intrinsics` via ProGuard `-assumenosideeffects`
- **Native library**: loads `libencrypt.so` from `app/libs/` through JNI
- **Baseline profile**: `app/src/release/generated/baselineProfiles/baseline-prof.txt` is *input*, not output — generated by `./gradlew :app:generateBaselineProfile` against a connected device (API 33+, no root) and committed, which is why the copy task says `IntoSrc`. R8 rewrites it per build and merges it with the profiles the libraries ship; what the APK carries is `assets/dexopt/baseline.prof`. It goes stale as the code moves, and a stale one still holds most of what it held.
- **`local.properties`**: stores per-machine SDK path; gitignored
- **Style**: the rules live in the root `.editorconfig` — import layout, line width 100, at most one blank line between declarations. Rules are switched off only by name in that file, and only after counting how much of the tree disagrees with them.

**Important**: Do not run `./gradlew` build commands. The user compiles manually and reports results.

## Architecture Patterns

### Data Flow (bottom-up)

```
API Server
  └─ Service (OkHttp: safeApiCall<T> → Result<ZhihuResponse>)
       └─ Repository (maps raw model → DTO, returns Result<DomainResult>)
            └─ ViewModel (manages UI state via mutableStateOf, calls repo in viewModelScope.launch)
                 └─ Composable Screen (observes ViewModel state, calls ViewModel actions)
```

### Layer Conventions

1. **`data/model/`** — Raw API response models, `@Serializable`, with `@SerialName` mapping. These mirror the Zhihu JSON structure exactly. A page reads them directly wherever the payload is already the shape it draws; the parser's own output carries them too (`RichTextElement.Image` holds a `ZhihuImage`), so this is vocabulary both layers share. What a model must not do is travel somewhere that has nothing to do with the payload it arrived in.

2. **`data/dto/`** — Flat, UI-ready data classes (no nested serialization). For where the UI wants a shape the payload does not have: a list row, a search hit, an unread summary. Marked `@Immutable` where applicable. A few of them carry an `AnnotatedString` built while mapping — a search hit's highlight, a message's markup — so `data/` is not free of Compose and does not pretend to be: the parser's output and these rows exist to be drawn.

3. **`data/mapper/`** — Extension functions that convert model → dto. Named `toDto()`. All are `internal`.

4. **`data/remote/service/`** — One class per API domain (FeedService, ContentService, UserService, etc.). Accept `OkHttpClient` via constructor. Use `safeApiCall<T>` extension for typed responses.

5. **`data/repository/`** — Wraps service calls, applies mappers, returns `Result<T>`. May define domain result classes (e.g. `FeedResult`).

6. **`data/remote/parser/`** — Transforms raw API segment lists into `RichTextElement` lists (Compose UI primitives). CPU-heavy; runs on `Dispatchers.Default`.

### Network Layer

- **`safeApiCall<T>(requestBuilder)`** — Extension on `ApiClient`. Executes on `Dispatchers.IO`, parses JSON via `kotlinx.serialization`, catches all exceptions and maps to `ApiException` sealed types. Returns `Result<T>`.
- **`safeExecute(requestBuilder)`** — Same, for writes whose response body is not needed; returns `Result<Unit>`. **Neither helper ever reports a non-2xx as a success** — both fail with an `ApiException` carrying the status code. Pick between them only by whether you need the parsed body.
- **`Response.body<T>()`** — `inline reified` extension that `use`-closes the response and decodes JSON. Throws `HttpStatusException` on non-2xx.
- **`offMain { }` / `mapOffMain { }`** (`core/exception/ResultExtensions.kt`) — move a mapping to `Dispatchers.Default`, one hop per page rather than one per row. A repository called from a ViewModel is on the main thread, so a page of models turned into DTOs there is main-thread work; `mapOffMain` is what keeps it off. Every `Result` a repository maps goes through it, because **a mapping that throws is a failure rather than an escape**: the transform is inside the `Result` contract, so nothing a parser or a mapper does can leave the caller's coroutine — which, for a ViewModel, would be past every `onApiFailure` and out to the thread's uncaught handler.
- Auth headers are injected by an OkHttp interceptor: `Authorization` and `x-udid` from `CredentialStore`, and the signature header from the native library — which a request with a sealed body does not carry. No `Cookie` header is written anywhere: that one belongs to the cookie jar.
- The funnel is also where the session is kept in hand — `SessionGate.awaitReady()` before a request goes out, `onExchange(status)` after each response, successful or not.
- **`HttpClientProvider`** holds the OkHttpClient singleton and a shared `Json` instance (lenient, coerce defaults, ignore unknown keys).
- **`HeaderProvider`** is an `object` that initializes the dynamic User-Agent via `WebSettings` at app startup, and produces the signature header through the native library.
- **HTTP log** — `HttpLogInterceptor` records API traffic into `HttpLogStore` (bounded, in-memory, newest first) for the in-app log screen. It records only requests to the `BASE_URL` host (Coil shares the same client), never records headers, and never writes to logcat. Failures are always recorded; the Debug-page toggle (prefs key `http_log_enabled`) additionally captures successful requests.

### DI (Koin)

Single module `appModule` in `di/AppModule.kt`. Uses DSL:
- `singleOf(::ClassName)` for services and repositories
- `viewModelOf(::ViewModelName)` for ViewModels
- `single { get<HttpClientProvider>().okHttpClient }` for the OkHttpClient instance
- `SharedPreferences` is provided as a `single` pointing to the `"temp_auth_prefs"` file
- `ApiClient` is what every service takes, because the funnel (`safeApiCall`/`safeExecute`) is an inline extension: anything it needs on every call has to hang off its receiver. Its `SessionGate` is resolved lazily — the gate needs a client of its own to talk to the server with, so the two cannot be built in either order
- `SessionManager` is bound under both its own type and `SessionGate`. Koin matches keys exactly, so an interface binding does not answer a request for the concrete type; the startup path asks for the manager and the funnel asks for the gate
- `UserSession` is a `single` caching the current user's hash id in memory, tagged with the access token it was resolved under, so a login, a sign-out or a drop to guest invalidates it by changing the token. It depends on `UserService` and `CredentialStore` and must never be made to depend on `UserRepository`; `CredentialStore` must stay in `core` for the same reason — either would form a DI cycle
- Koin is started in `Application.onCreate()` with `startKoin { ... }`, and an anonymous session is fetched immediately after

### Navigation

- **Type-safe routes**: `@Serializable` data classes/objects in `Route.kt`. Uses `navigation-compose` 2.9 type-safe API (`composable<RouteType>`, `toRoute()`).
- **`MainContainer`** is the start destination — it contains two tabs (Home, Profile) in a `HorizontalPager` with a `NavigationBar`.
- Detail screens (`AnswerDetail`, `ArticleDetail`, `PinDetail`, `QuestionDetail`, `PeopleDetail`, `Settings`, `About`, `OpenSourceLicense`, `ReadHistory`, `CollectionContents`, `HttpLog`, `DebugTools`, `Search`) are separate composable destinations pushed onto the NavHost stack. `DebugTools` is the one the settings page hides until the developer tools are unlocked. `PinDetail` uses a dedicated `PinDetailScreen` (thought page); `AnswerDetail`/`ArticleDetail` share `ContentDetailScreen`.
- **`Navigator`** — Wraps `NavHostController` + `Context` + `UriHandler`. Exposed via `CompositionLocalProvider` as `LocalNavigator`. Handles URL→route resolution via `LinkParser`.
- **`LinkParser`** — Parses Zhihu URLs, resolves `link.zhihu.com` redirects, extracts content type + ID from path patterns, returns `LinkDestination.Internal(route)` or `LinkDestination.External(url)`.
- Transition animations: horizontal slide (detail push = full right→left, pop = reversed with 1/5 parallax).

### State Management

ViewModels expose state via Compose `mutableStateOf` properties with `private set`. Pattern:

```kotlin
var uiState by mutableStateOf(UiState())
    private set
```

- **Optimistic updates**: Vote toggling updates state immediately, rolls back on API failure.
- **Pagination**: ViewModels track `nextPageUrl`, expose `loadIfEmpty()`, `refresh()`, `loadMore()`.
- **Load state**: `isLoading`, `isRefreshing`, `isNextLoading`, `globalError`, `loadMoreError` — each ViewModel defines its own UI State data class nested inside the ViewModel class. The page-level failure is `globalError`; a named sub-state (`LoadingState`, the comment sheet's three, the feedback sheet's) keeps its own `error`, which no paging field is there to be confused with.
- **Chunked parsing**: `ContentViewModel` parses segments in chunks of 10 on `Dispatchers.Default`, emitting incremental state updates for progressive rendering. Results cached in an `LruCache<String, List<RichTextElement>>`.
- **Sub-states**: a page whose state has outgrown one class splits it into named sub-states that travel together — `LoadingState` / `InteractionState` / `PresentationState` on the content pages, one per pane in the comment sheet. The split is for state with a lifecycle of its own, not for tidiness: a page that fits in one class keeps one.
- **Pin rendering**: `PinViewModel` handles the thought page separately. When a pin has no `structured_content` (image-only pins), it falls back to `image_list` to build `RichTextElement.Image` elements.

### Rich Text Rendering

The rich text pipeline:
1. API returns `List<Segment>` (paragraph, heading, blockquote, code_block, list_node, table, image, card, formula, etc.)
2. `ContentParser.transform(segments)` → `List<RichTextElement>` (sealed interface hierarchy of Compose-ready primitives). No mode and no color: one parse serves both themes, which is what lets its result be cached
3. Each `RichTextElement` renders via a corresponding composable in `ui/component/richtext/component/`
4. `ZRichText` composable wraps `Text` with clickable link interception and inline formula support via `InlineTextContent`

#### Formula rendering (image-based)

Formulas are **pre-rasterized images served by the Zhihu API**, not rendered locally:
- Each `Formula` carries `content`, `img_url`, and dp `width`/`height` (the PNG is 3x that). The API never omits these.
- `LatexComponent` (in `component/LatexComponent.kt`) loads the image via Coil `AsyncImage`. Inline and block formulas share the same component; block formulas are centered with no horizontal scroll.
- Sizing follows the values the API sends:
  - Image and `Placeholder` bounds use the exact server dp `width`/`height`, so formulas keep their natural size variation (simple subscripts ~13dp, display blocks up to ~164dp — 89dp and 164dp both occur in a single answer).
  - Widths are clamped to screen width minus 42dp (`constrainedSize`), scaling height proportionally — over-wide formulas are scaled down, never cropped or scrolled.
  - The dp→sp conversion divides by `fontScale` (`inlinePlaceholder`), so rendered pixels stay constant regardless of the user's system font size.
- A row is only as tall as its style asks for: Compose re-imposes an explicit `lineHeight` on a row a tall placeholder has grown, so a formula taller than the line would be drawn across its neighbors. Every host of an inline formula — `FormulaTextSection` for a paragraph, `ZRichText` for a heading, quote, list item, reference or table cell — takes its line height from `withFormulaLineHeight`, which raises it to the tallest formula plus 8dp of clearance.
- Dark mode inverts the white-background bitmap via a `ColorMatrix`, not a tint.

#### Code color (tokenizer-based)

The API sends a code block as `{content, language}` and nothing more — the server does no coloring, so the client tokenizes:
- `CodeHighlighter` (in `parser/CodeHighlighter.kt`, over `dev.snipme:highlights`) runs inside `ContentParser.transform`, on the same `Dispatchers.Default` as the rest of the body. It builds a fresh tokenizer per block, against the library's own advice to keep one around: the instance holds the analyzed code in mutable state, so a shared one would answer with a block another page parsed a moment earlier.
- The tokenizer answers with **eight sets of ranges that overlap** — only comments and strings are kept out of the keyword search, so the `.` in `// foo.bar` is punctuation and comment at once. They are laid down in the library's own order — the later set wins — and then cut into runs that never overlap, so a renderer adds them in the order it is handed them and the gaps keep the block's own color. Language names go through an alias table, because a fence is written by hand: `c++`, `js` and `bash` are not the spellings the tokenizer knows.
- `RichTextElement.Code` carries those runs and no color. Which color a kind gets is the renderer's, which is what lets one parsed body be cached and drawn in either mode.
- `SyntaxColors` (in `ui/theme/SyntaxColors.kt`) holds the palette, one arm per mode, and is its own rather than the scheme's. Every color clears 4.5:1 on the card it is drawn on, the dark arm measured against that card's own `#1A1F24`. Brackets, commas and the like are left unspecified, so they keep the text's color rather than making the block busier.
- A fence naming a language the tokenizer does not carry — `text`, and SQL, JSON, HTML and the rest — yields no runs, and the block draws in one color exactly as it did before there was a tokenizer.

### Error Handling

- `ApiException` is a sealed class: `NetworkException`, `UnAuthorizedException`, `NotFoundException`, `ServerException(code)`, `UnknownException`
- Each carries an Android string resource ID; `.uiMessage` is a `@Composable` extension property
- `ErrorView` and `LoadMoreErrorItem` composables in `component/common/` render error states with retry buttons

**Presenting a failed user action** — the shape follows the surface and the length, not taste.

A Toast is capped at two lines and truncates whatever does not fit, without saying so. Under that
budget it is the lighter notice of the two; over it, only a host can show the message whole.

| Surface | Use | Why |
|---|---|---|
| Screen with a `Scaffold` | `rememberActionErrorHost(viewModel.actionError, viewModel::consumeActionError)`, then `Scaffold(snackbarHost = { SnackbarHost(state) })` | the host can carry it |
| Screen that pops itself on success, whose wording fits those two lines (`LoginScreen`) | Toast, for its failures as well as its success | the success notice has to outlive the screen, and its failure answers the same tap |
| `Dialog()` (`CollectionDialog`) | render `error.uiMessage` inside the dialog | it draws in its own window; the host's snackbar would be hidden behind it |
| App-level non-Composable (`Navigator`) | Toast | no `SnackbarHostState` is reachable, and it outlives the current screen |
| Reusable widget with no host parameter (`ImageLightbox`) | Toast inside the widget | cannot require every call site to supply a host |
| Surface with no `Scaffold` (comment bottom sheet, the message tab) | `ErrorView` / `LoadMoreErrorItem` inside the surface; a Toast for a tap's own answer | there is no host to use |

A Toast is capped at two lines and truncates whatever does not fit, without saying so — so where the
table above reaches for one, the wording has to fit on its own, since a surface with no host has
nothing else to show it. A page that failed to load is not that case: it draws its error inside
itself, host or not.

Do not pass a snackbar host down through a `CompositionLocal`: two of these rows have no host to reach at all.

## Key Conventions

- **All properties in API models have defaults** (empty strings, 0, null, empty lists) — never assume mandatory fields from the server.
- **Mappers are `internal`** — not exposed outside the `data.mapper` package.
- **Services use `Result<T>`** — never throw; all failures are caught and wrapped.
- **Handling a failed `Result`** — use `onApiFailure { error -> … }` (`core/exception/ResultExtensions.kt`), never `Result.onFailure` directly. It is the only place cancellation is filtered out of the failure path, and its callback always receives a non-null `ApiException`, so a failure cannot become a silent no-op. Never `runCatching` inside a coroutine — it swallows `CancellationException`.
- **Discarding a `Result`** — only via `ignoreOutcome()`, so that "we do not care about this one" stays greppable instead of looking like a forgotten check.
- **Taking a page into a list** — a list drawn under a key taken from the row (`key = { it.id }`) takes every page in through `withPage(page, firstPage) { it.id }` (`core/utils/compose/LazyListExt.kt`), never `held + page`. A key measured twice throws where the row is drawn, and a page can carry a row an earlier one already handed over — the append is where that is dropped, in one place rather than at each call site.
- **`@Immutable`/`@Stable`** annotations on data classes consumed by Compose for stability inference.
- **Composable parameters**: required first, then `modifier: Modifier = Modifier`, then what is optional, with a trailing `content` lambda last — the order Material's own components use. A required callback belongs with the other required parameters, not parked after `modifier`.
- **String resources** are in `res/values/strings.xml` (English) and `res/values-zh-rCN/strings.xml` (Chinese). Always reference via `R.string.*`, never hardcode user-facing strings.
- **Credentials**: The session lives in `SharedPreferences` (`"temp_auth_prefs"`) behind `CredentialStore`, read fresh on every request so a write reaches the next one with nothing having to be told. It also publishes the session as a `StateFlow`, for what draws the session rather than requests it — a screen has no request of its own that would come back and tell it. Cookies are not among them; those are the cookie jar's. DebugScreen manages the device id only, and `http_log_enabled` shares the file and survives.
- **Screen navigation**: Use `LocalNavigator.current` inside screens for item-click navigation (see `ReadHistoryScreen`, `CollectionContentsScreen`). Do NOT pass `onItemClick: (String, String) -> Unit` callbacks from NavGraph — the screen resolves its own navigation via `navigator.navigateToContent(id, type)`. This keeps NavGraph entries thin and avoids callback threading through multiple layers.
- **A ViewModel action is not navigation**: a composable that takes a `viewModel:` parameter must not hand anything *derived from it* to another composable — `remember(viewModel) { viewModel::openFeedback }` passed into a list row is `ComposeViewModelForwarding`, an error that fails `./gradlew lint`. Such a callback arrives as a parameter instead, from a caller that holds the ViewModel as a local (`MainScreen`'s `val feedViewModel = koinViewModel()`), which is not a forwarding. The bullets above still stand: a callback carrying no ViewModel belongs inside the screen.

## Git Conventions

- Commit format: `<type>: <description>` header, blank line, `- ` bullet list of changes, optional closing paragraph for motivation. Types: `feat`, `fix`, `refactor`, `build`, `docs`, `test`, `chore`.
- Split by story, not by motive or by layer: one commit is one change the repo can be described as having made, told end to end. A fix that runs through the layers — the parse that carries something and the drawing that shows it — is one commit; two changes that merely share a reason are two. Nothing lands that only makes sense once the next commit is in.
- Never run destructive git commands (force push, hard reset, skip hooks) without explicit approval
